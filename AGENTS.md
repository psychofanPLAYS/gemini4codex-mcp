# Agent Collaboration & Development Guide

> **Context**: You are reading the internal development guide for the `gemini4codex` MCP Delegator repository. This guide explains the architecture, the relationship between Codex and Gemini, and how to safely modify this project.

## 1. Perspectives & Roles

### Codex (The Primary Orchestrator)
- **Role**: You are the human-facing Architect. You make the final design decisions, plan workflows, and delegate isolated tasks using the MCP tools (`delegate_to_agent`, `apply_agent_run`).
- **Responsibility**: You must review the `git diff` generated by your subordinates before committing code to the main branch. You are the ultimate gatekeeper of the user's project.

### Gemini (The Subordinate Worker)
- **Role**: Background execution engine. The Gemini workers are instantiated dynamically by this MCP server using the Google Antigravity SDK.
- **Responsibility**: They run in strict isolation (`.worktrees/wt-<uuid>`) and are natively jailed. They do not talk to the user and cannot auto-commit changes. Their global invariant rules are defined in `GEMINI.md`.

## 2. Antigravity SDK Primer (For Codex)

If you (Codex) are modifying the MCP's Python source code, you need to understand how the `google-antigravity` SDK is used in `server/supervisor.py` and `server/security.py`, as you likely do not have its training data:

1. **`LocalAgentConfig`**: The configuration object used to instantiate a Gemini worker. 
   - `model`: e.g., `gemini-3.6-flash` or `gemini-3.1-pro`.
   - `instructions`: The system prompt. We inject the contents of `GEMINI.md` here.
   - `hooks`: An array of security interceptors.
2. **`Agent`**: Instantiated with the `LocalAgentConfig`. We trigger it asynchronously using `await agent.chat(prompt)`.
3. **Security Hooks (`@hooks.pre_tool_call_decide`)**: The Antigravity SDK allows us to intercept tool calls *before* they execute. In `security.py`, we use this to aggressively block destructive OS commands, prevent the worker from bypassing the OS sandbox (`BypassSandbox=True`), and lock its write access to the specific target workspace.
4. **Structured Outputs**: We pass a Pydantic model (`WorkerRunOutput`) to `response_schema` in the config. When the worker finishes, the SDK automatically forces its final response into this structured JSON format.

## 3. Development Guidelines for this Repository

When adding features or fixing bugs in this `gemini4codex` repository, adhere to the following invariant rules:

- **Strict Sandbox Enforcement**: Never loosen the restrictions in `security.py`. Subordinate workers must never be allowed to run `git commit`, `git push`, or pass `BypassSandbox=True` to the native `run_command` tool.
- **No Auto-Committing**: The `WorktreeManager.apply_run` function in `worktree.py` uses `git merge --squash`. It must **never** automatically commit the changes. The changes must remain staged in the index so Codex or the user can review them.
- **SQLite Ledger Integrity**: State is managed in a WAL-mode SQLite database (`ledger.py`). Do not perform blocking file I/O operations on the main FastMCP thread.
- **Dependency Management**: This project relies on `uv` and requires **Python 3.10+** (due to the `fastmcp` dependency). If you add new dependencies, ensure you run `uv lock` (with `BypassSandbox=True` if you are a Gemini worker developing on this repo) to pin them.
